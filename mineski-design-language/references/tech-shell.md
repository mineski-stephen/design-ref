# Tech shell

The shape that keeps tools easy to hand over: a static site anyone can deploy
by uploading files, with secrets kept on small proxies.

## Repository layout

```
index.html               the page (all views as <section class="view">, dialogs, toasts host)
manifest.webmanifest     home-screen install
css/theme.css            generated by tools/make_theme.py
css/mineski-base.css     copied from this skill, unedited
css/app.css              this tool's few extra styles (tokens only)
js/icons.js  js/ui.js    copied from this skill (add icons in the same style if needed)
js/session.js            copied from mineski-systems-design/assets, unedited: the Lark login shared by every tool
js/config.js             APP (with version), SERVICES, LARK, TABLES, RULES (see mineski-systems-design §3). No secrets.
js/app.js                state, routes, views
js/<area>.js             one module per area (net.js, auth.js, errors.js, schema.js, verify.js, inbox.js…)
img/<tool>-icon.svg + -32.png -180.png -512.png
tools/serve.py           the local dev server, copied from this skill's tools/ (PORT = the tool's registered port)
.claude/launch.json      runs `python tools/serve.py` on that port
package.json             no dependencies; scripts serve, test, check:live, check:proxy, check:shell (…)
.env.example             names of the admin secrets for Node/Python scripts; the real .env is git-ignored
README.md                for the team (see below)
CHANGELOG.md             every change and version update, newest first; its top entry = APP.version
render/<service>/        the proxy, if the tool has its own (Python stdlib, Dockerfile, render.yaml)
tests/                   offline tests of the pure logic, live checks, the ?preview shim and fixture
```

The backend half (Lark login, data access, networking, proxies, storage,
tests, ports) is specified in **`mineski-systems-design`**; this file covers the
page shell. No build step, no framework, no npm runtime dependencies. ES modules with one
global-free `app.js` entry. Third-party libraries (PDF, image conversion) come
from cdnjs with SRI and an exact version, and are **lazy-loaded** when the
person first needs them (e.g. on "Download PDF").

## `<head>` boilerplate (in this order)

1. `charset`, the three no-cache `http-equiv` metas, `viewport` with `viewport-fit=cover`.
2. `<title>Tool · Mineski</title>` (views update it: "All briefs · Fetch") and a one-sentence description.
3. `theme-color` twice, with the light and dark `--bg`, `media="(prefers-color-scheme: …)"`.
4. Icons: SVG favicon, 32px PNG, 180px apple-touch-icon, the manifest.
5. Google Fonts preconnects + the one family, weights 400-800, `display=swap`.
   Then `<meta name="referrer" content="strict-origin-when-cross-origin">` and a
   Content-Security-Policy `<meta>` whose `connect-src` lists only `'self'`, the
   tool's proxies and `http://127.0.0.1:*` for local overrides.
6. The inline theme script (before any CSS):
   ```html
   <script>try { var t = JSON.parse(localStorage.getItem("tool.theme")); if (t === "light" || t === "dark") document.documentElement.dataset.theme = t; } catch (e) {}</script>
   ```
7. The cache-busting loader: a build id per page load (`window.APP_BUILD`), styles written with
   `?v=<id>`, and an import map that maps every module to `?v=<id>` so imports
   are fresh too. See `templates/starter/index.html`; list every JS file in it.
8. The module entry at the end of `<body>`, also with `?v=`.
9. A boot watchdog after it (see `templates/starter/index.html`): if `app.js`
   hasn't set `<html data-booted>` within about 8 s, show "<Tool> couldn't
   start. Reload the page." with a Reload button. One failed module (or opening
   the page from a file) otherwise leaves a dead page. `app.js` sets it as the
   last line of its start-up.

Body skeleton: skip link → `.bg` → `header.topbar` → `main#main[tabindex=-1]`
→ `dialog`s → `div#toasts.toasts[aria-live=polite]`.

## State and rendering

- One state object `S`; `render()` derives the DOM from it. Views toggle with
  `.view.active` (the base CSS hides every other `.view`). Routes come from
  `location.hash`; each view sets `document.title` ("All briefs · Fetch").
- View modules are factories that take a `ctx` object; shared modules offer
  subscriptions (`service.on`, `auth.onEnded`, `auth.onShared`) rather than global DOM events.
- Build DOM with `h()`; set text, never HTML from data.
- Re-render only the part that changed; never rebuild an editable document
  while the person is editing it.
- Keep pure logic (rules, mapping, normalizing) in plain functions in their own
  module so it can be tested offline with fixtures from real data quirks.

## Storage

| What | Where | Key |
| ---- | ----- | --- |
| Theme, tab, view preferences | `localStorage` | `<tool>.theme`, `<tool>.tab`, … |
| Dev overrides, personal settings | `localStorage` | `<tool>.settings` (one JSON object) |
| Drafts (with their `client_token`), cached lists | `localStorage` | `<tool>.draft`, `<tool>.cache.<app>:<table>` |
| The login, shared by every Mineski tool on the site (never in a URL) | `localStorage`, through `js/session.js` only | `mineski.auth.token` / `.user` (see `mineski-systems-design` §4.2) |
| A login in progress | `sessionStorage` (this tab only) | `<tool>.auth.pending` |
| Typed-but-unsaved text, tab-scoped overrides | `sessionStorage` | `<tool>.<name>` |

Every access goes through `store()`/`recall()` (JSON only, never throw). Normalize
anything read back (old shapes from earlier versions must still render). Renaming
a key uses a dated inline migration in `<head>` (see `mineski-systems-design` §9;
`fetch/index.html` and `polaris/index.html` have working examples).

## Backends: Lark and proxies

- **Lark Base is the database.** Read tables in full (not through a view, which
  can hide rows), check columns, types and select options on load, and switch
  off only the affected actions if something doesn't match.
- **Every Lark call runs as the signed-in user** (OAuth + PKCE through the shared
  Lark proxy, which adds the app secret), so Lark applies their own permissions.
  Logins last about 2 hours; there is no refresh token.
- **Secrets live on proxies** (Render web services, env vars), each exposing one
  narrow job ("extract a brief", not "call Gemini"). The page never holds a secret.
- Free Render services sleep: ping `/` on page load to wake them; retry reads
  (not writes) with backoff for up to ~3 minutes; detect ad blockers.
- Writes: idempotent creates (`client_token`), re-check before writing, read back after.
- `describe(err)` maps backend codes to one plain sentence each (see `copy-and-voice.md`).
- Configuration (table links, labels, rules, `ENV_LABEL` for "Test copy") lives
  in `js/config.js`. A developer-only `?preview` mode on localhost may run on a
  fixture with writes simulated; it shows a red badge and never ships real data.
- The full rules for all of the above (timeouts, retry schedule, schema specs,
  safe writes, read-back, error messages, proxy versioning, ports, tests) are in
  `mineski-systems-design`.

## Hosting

GitHub Pages (or any static host) over https. Register the exact page address
(with trailing slash) as a Lark redirect URL. Add the address of each
environment: `http://127.0.0.1:<the tool's registered port>/` and the Pages URL. Phones can "Add to Home Screen".

## README for the team

Every tool's README has, in this order: one paragraph on what it does and for
whom (with the icon); Contents; **Using it** (numbered steps in the team's
words); what it reads and writes; Settings; how it's built (a small diagram);
running locally; deploying; design decisions; security and privacy; known
limits; **Troubleshooting** (a table of the exact messages people see → what to
do); maintenance recipes (add a field, rename a column, move tables); files.
